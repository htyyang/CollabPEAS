Part A - Symmetric Collaborative Architecture
A1. Network Topology and Session Structure
The system uses Photon Fusion 2 with Shared Authority topology — the same topology
used in the drone project. There is no dedicated host; both participants are peers. In the
symmetric model, both participants hold equal StateAuthority potential over all shared
objects. Authority transfers dynamically: whichever client initiates a grab or UI interaction
claims StateAuthority on that object for the duration of the interaction.

NetworkRigVariant. Replace the drone's LearnerActivitiesPrefab with your BlockCanvasPrefab.
Both players spawn with identical rig configurations — no role flag is set.

A2. Symmetric Access
Both participants' grab colliders are always active on all blocks. Both participants can press
Robot POV, stamp the observation log, use vibe coding, and trigger trace highlights.
Simultaneous Grab Conflict Resolution
When both participants attempt to grab the same block at the same moment, Fusion's
StateAuthority transfer resolves the conflict automatically: the first client to call
RequestStateAuthority() wins. The other participant's grab attempt fails silently — their hand
passes through the block (0.3s) and the block remains with the first grabber.
This is the same conflict resolution mechanism the drone project uses when multiple learners
reach for the same drone part simultaneously. No additional code is required.
🔧 DRONE PROJECT REFERENCE
Feasibility: Direct reuse — drone's grabbing system is identical
Module to borrow: XRShared local rig grabbing + NetworkTransform on each block prefab
How to adapt: The drone uses local rig grabbing where any learner can grab any part. Each
drone part has a NetworkTransform that syncs position to all clients. Apply the same component
to each block prefab. When either participant grabs a block, that client calls
RequestStateAuthority on the block's NetworkObject. The other participant sees the block
moving via NetworkTransform interpolation.
Code note: block.GetComponent<NetworkObject>().RequestStateAuthority(); // called on grab by
either player

A3. Shared Block Canvas — Network Sync
When either participant places, moves, or removes a block, the change must be visible to
the other within one network tick (~50ms on LAN,
~100ms on typical WiFi). The
SharedRuleSet NetworkArray is the single source of truth. Any client can write to it when
they hold StateAuthority.
🔧 DRONE PROJECT REFERENCE
Feasibility: Adapt from drone — medium eﬀort
Module to borrow: LearningManager.ActivitiesAvailability (NetworkDictionary) → adapt as
SharedRuleSet (NetworkArray)
How to adapt: The drone's ActivitiesAvailability is a NetworkDictionary<int, ActivityStatus> that
all clients read but only StateAuthority modifies. Replace with NetworkArray<RuleData> of
capacity 20. When either participant snaps a block into a slot, that client transfers StateAuthority
over SharedRuleSet and writes the new rule entry. Fusion's OnChangedRender fires on all

Voice is the primary coordination mechanism in the symmetric model. Because neither
participant is constrained to a specific role, verbal negotiation —
"I'll do the sensors, you

Shows a live preview of the robot, with sensors appearing as mounted modules on

The slot counter at the top of the library panel displays how many unique sensors
have been placed across all tasks — a student can assign the same sensor to
multiple tasks without using additional slots, since the same physical sensor module
serves all tasks simultaneously. The maximum is 11 slots, matching the number of

proceed to the percept summary screen, which shows two columns: what the robot
can now perceive, and what it cannot perceive given the sensors that were not
selected. This summary is the bridge between sensor selection and the Robot POV
mode that follows, making the bounded percept sequence concept explicit before
students inhabit the robot's perspective.

Step 4 - Program Your Robot: Vibe Coding
PEAS: All four PEAS components
Learning Objectives: LO2 (construct full PEAS description), LO7 (trace perceive–decide–act
cycle)
Competencies: C8 (Decision-Making), C17 (Programmability)
Purpose: Step 4 is where students translate their sensor and actuator selections from
Steps 2 and 3 into executable decision logic. Using physical block manipulation, both
participants construct a set of rules — one per task — that govern how their robot
perceives its environment, evaluates conditions, and acts. Every rule follows a strict
four-slot chain:
SENSE block
What can the robot
perceive?
CONDITION block
Under what condition?
ACTION block
What should the robot
do?
CONTROL block
How long / what priority?
All block logic is pre-coded. Students cannot write or modify code, they decide which blocks
to combine. The code inside each block runs exactly as specified in the Block Library
document. The six rules run in parallel during Step 5: whichever sensor fires first in a given
tick triggers that rule's action. Rules do not execute in sequence; the robot is driven by the
environment, not by a script.

Implementation Notes
6.1 — Rule validation logic
A rule chain is valid and executable when it contains at minimum one SENSE block and one
ACTION block. A CONDITION block without a compatible SENSE block in the same chain
must be flagged with a yellow broken-link indicator on the canvas — but not removed. The
student can fix it by adding the correct SENSE block. A CONTROL block without an ACTION
block should be flagged similarly.
6.2 — Tick-based execution
The robot simulation runs on a fixed tick (recommended: 10 ticks per second). Each tick,
the robot evaluates all active rules in the SharedRuleSet. Rules without a CONTROL block
fire once per tick while their condition is true. REPEAT UNTIL and REPEAT WHILE fire every
tick. WAIT pauses the rule for a fixed number of ticks (2 seconds = 20 ticks at 10 Hz).
PRIORITY resolves conflicts: if two rules fire in the same tick, the HIGH priority rule wins and
the other is suppressed for that tick only.
6.3 — PlayerID tagging
Every block placement, removal, and swap event must be logged with the PlayerID of the
participant who triggered it, a timestamp, and the sequence order within the session. This
is required for RQ3 contribution analysis. The PlacedByPlayerID field in the RuleData struct
(defined in Part A of the design flow document) stores this information at the rule level.
Individual placement events are stored separately in the session event log.
6.4 — Broken link visual feedback
When a CONDITION block is placed without a compatible SENSE block: the CONDITION
block glows amber on the canvas and a floating label reads 'This condition needs a sensor
— add the matching SENSE block to complete this rule.
' When a student adds the correct
SENSE block, the amber glow clears. This feedback must be visible to both participants
simultaneously via Fusion sync.

Verbal Agreement Protocol (Symmetric)
Before either participant executes any debug move, the system displays a 2-second prompt
(visible to both): 'What caused this? Discuss before changing anything.
'
This prompt is not a gate — it disappears after 2 seconds and does not lock interaction. But it
creates a structured moment for verbal coordination. Either participant can proceed after the
prompt fades. The verbal discussion that follows is a primary data source for the post-session
interview and for analyzing collaborative decision-making patterns in the symmetric model.
5.4 - PEAS Reflection Prompt (Spatially Embedded)
When a performance score drops, the thought-bubble prompt appears near the failing
robot in 3D space. Both participants see it simultaneously — it is a shared spatial object,
not a per-player UI element. Either participant may select the answer.
PEAS Reflection Prompt Text
'Your robot just [behavior]. This aﬀected your [dimension] score.
'
'Before you change anything: is your robot behaving irrationally — or rationally with a wrong
specification?'
Either participant selects on behalf of the pair:
◦ My sensor doesn't detect what I expected
◦ My decision rule fires at the wrong time
◦ My actuator can't do what my performance measure requires
◦ My performance measure weights are set incorrectly
5.5 - Closing C1 Reflection (Both Participants — Individual)
At the end of the final iteration, before the summary screen, both participants respond to
the closing reflection prompt separately. This is the second moment (after 1A) where
individual responses are required — both answer simultaneously but independently. This is
a measurement task, not a design task.

Contribution Analysis in the Symmetric Model
In v4, role assignment (Builder/Observer) provided a structural basis for comparing individual
contribution. In the symmetric v5 model, contribution is measured through behavioral logs:
• Block placement ratio: did one participant place significantly more blocks than the other?
(Dominant coder pattern)
• POV usage: did both participants enter Robot POV, or only one? (Self-organized division vs.
joint experience)
• Log stamping ratio: did stamping divide evenly, or did one participant specialize in observation?
• Debug initiation: who initiated Debug Move 1/2/3 more often?
These patterns, analyzed alongside post-session individual knowledge tests, allow the study to
examine whether natural role emergence in a symmetric design produces learning outcomes
comparable to enforced role division — a genuine empirical contribution absent from v4.
